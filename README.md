## 🧭 한눈에 보기

| 항목 | 내용 |
|---|---|
| 입력 | 상품 사진 1~6장(JPG · PNG · WebP), 상품명, 설명 몇 줄 |
| 출력 | 폭 860px 긴 PNG · JPG 한 장, 섹션별 PNG |
| 사용 방식 | 로컬 웹 화면. 왼쪽 채팅, 오른쪽 실시간 미리보기 |
| 모델 | 텍스트 · 비전 Qwen3.8-9B, 사진 편집 Qwen-Image 2.1. 모두 이 Mac의 MLX Serve |
| 외부 호출 | 없음. 모델은 로컬 MLX Serve만, 폰트는 시스템 폰트 |
| 범위 밖 | 로그인 · 다중 사용자 · DB · 클라우드 배포 · 스트리밍 응답 |

이 에이전트가 지키는 원칙은 세 가지입니다.

1. **업로드 원본은 바꾸지 않습니다.** 사진 편집은 늘 원본에서 시작해 새 파일로 저장합니다.
2. **없는 사실을 지어내지 않습니다.** 상품명 · 설명 · 대화에 없는 숫자는 기계 검사로 막고, 숫자가 아닌 사실은 판정 모델이 문장마다 검사합니다.
3. **모르면 묻습니다.** 무게 · 소재처럼 꼭 필요한데 없는 사실은 지어내지 않고 사용자에게 되묻습니다(`ask_user`).

## 🏆 포트폴리오 요약

> 이력서 · 포트폴리오 · 면접에 옮겨 쓰기 좋게 정리했습니다. 수치는 모두 이 저장소의 [파인튜닝 보고서](docs/finetune), [측정](#measure), [LangSmith 로그 점검](#log-review)에서 가져왔습니다.

**한 줄 요약.** 상품 사진과 설명 몇 줄을 받아 상세페이지 초안을 만들고, 채팅으로 고쳐 860px 이미지로 내보내는 로컬 LLM 에이전트입니다.

- Qwen3.8-9B와 Qwen-Image 2.1을 노트북(MLX)에서만 돌립니다.
- LangGraph로 흐름을 짜고, 사실 검사를 여러 겹으로 둬서 없는 사실을 지어내지 않게 했습니다.
- 판정 모델과 문구 모델의 파인튜닝은 블라인드 평가로 채택 여부를 정했습니다.

### 내가 한 일

**에이전트 설계 · 구현**
- LangGraph 그래프 두 개를 만들었습니다.
  - 첫 초안: `analyze → caption → write_copy → assemble → check → edit_scene → first_message`, 고정 순서 7노드입니다.
  - 채팅 한 턴: `model ⇄ tools` 순환입니다. 텍스트 답 · `ask_user` · 4라운드 중 하나로 끝납니다.
- 도구 8개를 만들었습니다. 문구 수정 · 사진 편집 · 사진 교체 · 섹션 추가/삭제/이동 · 배치 변경 · 되묻기입니다.
- 도구 오류는 예외가 아니라 모델에게 돌려주는 문장으로 설계했습니다. 모델이 그 문장을 읽고 스스로 다시 시도하거나 사용자에게 묻습니다.
- 버전 저장과 되돌리기, 업로드 형식 판별, 파일 경로 검증, 요청 하나씩 처리하는 잠금을 넣었습니다.

**환각 방지 (여러 겹 검사)**
- 1겹: 상품명 · 설명 · 대화에 없는 숫자는 기계 검사로 막습니다.
- 2겹: 최상급 · 한자 표현을 규칙으로 거릅니다.
- 3겹: 문장마다 9B 판정 모델이 근거를 확인합니다. 판정을 못 하면 초안을 만들지 않습니다(fail-closed).
- 무게 · 소재처럼 꼭 필요한데 없는 사실은 `ask_user`로 사용자에게 묻습니다.

**LangChain · LangGraph 전환**
- 직접 HTTP로 부르던 모델 층을 LangChain `ChatOpenAI`로 옮기고, 에이전트 흐름을 LangGraph로 옮겼습니다.
- 합격 기준은 "동작은 그대로"였습니다.
  - 에이전트 · 서버 테스트는 내용을 고치지 않고 통과해야 합니다.
  - 실모델 회귀가 기준 이상이어야 합니다.
  - 초안 시간이 10% 넘게 늘면 안 됩니다.
  - 앱을 기본 설정으로 띄우면 LangSmith로 아무것도 나가지 않아야 합니다.
- 결과는 모두 기준 안이었습니다.
  - 사진 2장 초안이 63.2초에서 64.1초가 되었습니다(+1.4%).
  - 실모델 회귀는 도구 12/13 · 판정 8/8이었습니다.
  - `LANGSMITH_TRACING=true`로 서버를 띄워도, 초안을 만드는 동안 밖으로 나가는 연결이 없었습니다.

**평가 · 파인튜닝 체계**
- 평가 장치(`copy_eval.py`)를 만들었습니다.
  - 상품을 분류마다 dev · test · train으로 나눕니다.
  - 블라인드 A/B 짝을 만들고, 좌우는 고정 시드로 섞고 열쇠는 따로 둡니다.
  - 판정자는 맥락 없는 서브에이전트로, 짝 파일만 봅니다.
  - 기계 지표는 허용 폭과 비교합니다.
- 학습 전 관문을 뒀습니다. 교사 데이터가 dev에서 기준선을 이겨야만 학습 시간을 씁니다.
- LoRA SFT를 진행했습니다. mlx-vlm으로 학습하고 8bit로 병합해 MLX Serve에 올렸습니다.

### 문제 해결 사례

#### 사례 1. 좋아 보이던 판정 파인튜닝을 버린 이유: 치우친 평가셋

- **상황.** 사실 판정 9B를 LoRA로 학습했습니다. 정답은 Codex가 매겼습니다.
- **문제.**
  - 개발용 평가셋에서 r1은 F1 0.826으로 원본(0.609)보다 좋아 보였습니다.
  - 그런데 실모델 회귀에서 "이중 진공 단열로 따뜻함이 오래가요"처럼 근거 있는 문장을 걸렀습니다.
- **원인.**
  - 개발용 평가셋은 Codex 정답을 검토해 16개만 고친 것이었습니다. 그래서 교사 쪽으로 치우쳐 있었습니다.
  - 교사를 보지 않고 새로 매긴 150문장 시험셋에서 다시 쟀습니다. 원본은 F1 0.814 · 잘못 거르기 0.057이었고, r1 · r2는 잘못 거르기가 0.46 · 0.39였습니다.
  - 교사(Codex) 자체도 시험셋에서 0.284를 잘못 걸렀습니다.
- **결정.** 학생은 교사를 넘기 어렵습니다. 그래서 2시간 30분짜리 r3 학습을 돌리지 않고, 판정은 원본으로 두었습니다.
- **배운 점.**
  - 학습 전에 교사와 무관한 블라인드 시험셋부터 만들어야 합니다.
  - 학습에 시간을 쓰기 전에, 교사가 시험셋에서 얼마나 맞는지 먼저 재야 합니다.
  - 이 순서는 이후 문구 단계의 규칙이 되었습니다.
- 근거: [r1 보고서](docs/finetune/2026-10-16-judge-r1-report.md), [r3 보고서](docs/finetune/2026-10-17-judge-r3-report.md)

#### 사례 2. 프롬프트로 안 되던 것을 SFT로: 문구 품질

- **상황.** 첫 초안 문구가 프롬프트 예시를 그대로 베끼고(0.967), 근거 없는 효과를 지어냈습니다.
- **1차 시도 (프롬프트 개선 2-1).**
  - dev에서 세 판을 고쳐 승률 0.633으로 합격했습니다.
  - 그러나 test에서는 0.414(12승 17패)로 떨어졌습니다.
  - 금지 목록에 넣은 유형이 이름만 바꿔 다시 나왔습니다. dev에 맞춘 과적합이었고, 채택하지 않았습니다.
- **2차 시도 (조건부 SFT 2-2).**
  - Codex 교사 초안을 먼저 관문에 올렸고, dev에서 30/0/0으로 통과했습니다.
  - 학습 상품 240개에서 초안 480개를 만들었습니다.
  - 그 초안을 런타임 검사(숫자 · 최상급 · 한자 · 9B 판정)에 그대로 통과시켰습니다. 하나라도 걸린 초안은 버렸습니다(버린 비율 0.273).
  - 남은 학습 349행 · 검증 23행으로 LoRA를 학습했습니다(32분, 최대 메모리 10.1GB).
- **결과.**
  - test 블라인드 승률 0.897을 얻었습니다.
  - 지어낸 사실 비율 0.146 → 0.049, 예시 베끼기 0.967 → 0.3입니다.
  - 2-1에서 0승 6패였던 화장품이 5승 1패가 되었습니다.
- **배운 점.**
  - 프롬프트로 금지를 늘리는 것보다, 검사를 통과한 좋은 예를 보여 주는 편이 지어내기를 더 줄였습니다.
  - dev 점수는 test 점수의 약속이 아닙니다.
- 근거: [2-1 보고서](docs/finetune/2026-10-17-copy-2-1-report.md), [2-2 보고서](docs/finetune/2026-10-18-copy-2-2-report.md)

#### 사례 3. 최종 리뷰에서 잡은 범위 밖 입력: 채택 모델의 사용 범위 좁히기

- **상황.** 2-2를 채택한 뒤 브랜치 전체 리뷰를 했습니다. 학습과 시험이 모두 "사진 설명 없음" 입력만 썼다는 지적이 나왔습니다.
- **검증.** 사진 설명 2개를 붙인 상품 10개로 따로 쟀습니다. details를 정확히 2개 쓴 초안이 원본은 10/10, 2-2는 3/10이었습니다.
- **조치.**
  - 런타임 `write_copy`는 사진 설명이 있으면 원본 모델을, 없을 때만 문구 모델을 쓰게 했습니다.
  - 고치기 전에 실패하는 테스트를 먼저 썼고, 고친 뒤 통과하는 것을 확인했습니다.
  - 교사 초안 행에는 만들 때 쓴 프롬프트의 해시를 남겨, 다른 프롬프트로 만든 행이 학습 데이터에 섞이면 거부하게 했습니다.
- **배운 점.** "평가에서 이겼다"는 평가한 입력 분포 안에서만 유효합니다. 채택 범위를 측정 범위에 맞췄습니다.
- 근거: [2-2 보고서 "사진 설명이 있는 입력"](docs/finetune/2026-10-18-copy-2-2-report.md)

#### 사례 4. LangSmith 로그를 직접 읽어 찾은 추적 누수

- **상황.** LangSmith 월간 한도가 차서 429가 났습니다. 그런데 앱 서버는 기본으로 추적을 끄도록 되어 있었습니다.
- **조사.** LangSmith API로 프로젝트와 run을 직접 집계했습니다.
  - `pagegen-dev`에 trace 2,273건 · 토큰 211만이 쌓여 있었습니다.
  - 그중 LangGraph trace 117건의 입력이 모두 테스트 고정 데이터였고, 한 건이 0.03초 안에 끝났습니다.
- **원인.**
  - 테스트가 학습 스크립트 모듈을 import하면, 그 모듈이 import 시점에 추적을 켰습니다.
  - 전체 실행에서는 서버 테스트가 다시 꺼서 드러나지 않았습니다. 일부 파일만 돌릴 때만 새어 나갔습니다.
- **조치.**
  - `conftest.py`가 추적 변수를 먼저 `false`로 고정하게 했습니다.
  - 이 테스트만 따로 돌리면 실패하던 회귀 테스트를 추가했습니다.
- **배운 점.** 관측 도구도 관측해야 합니다. 실제 앱 실행은 한 번도 추적되지 않았다는 사실도 이 조사에서 확인했습니다. 실데이터는 밖으로 나가지 않는다는 원칙이 지켜졌다는 뜻입니다.
- 근거: [LangSmith 로그 점검](#log-review)

#### 그 밖의 작은 사례

- **긴 JSON의 반복 루프.**
  - 분석과 문구를 한 번에 긴 JSON으로 받으면, 9B가 같은 문장을 반복하다 출력 한도에서 잘렸습니다.
  - 그래서 호출을 둘로 나눴습니다.
  - JSON이 깨지면 한 번만 다시 부르고, 또 깨지면 초안을 만들지 않습니다(업로드 사진은 남김).
- **조용히 틀리는 모델 서버.**
  - MLX Serve는 없는 모델 이름을 받으면 오류 없이 이미 올라온 모델로 답합니다.
  - 평가 스크립트가 서버의 모델 목록을 먼저 확인하고, 목록에 없으면 거부하게 했습니다.
- **잘못 잰 토큰 길이.**
  - `apply_chat_template(tokenize=True)`가 BatchEncoding을 돌려줘서, 모든 학습 행의 길이가 2로 재졌습니다.
  - 템플릿 문자열을 만든 뒤 토크나이즈해서 다시 쟀습니다(최대 913 토큰). 그 값으로 `max-seq-length 2048`을 정했습니다.

### 설계 결정과 이유

| 결정 | 이유 |
|---|---|
| 모델 전부 로컬(MLX) | 판매자의 실제 상품 정보가 밖으로 나가지 않게. LangSmith도 개발 · 학습 합성 데이터에만 씀 |
| 레이아웃 · 문구는 HTML 템플릿, 이미지 모델은 업로드 사진 편집(연출 컷)만 | 문구가 HTML 텍스트여야 채팅으로 고치고 사실 검사를 할 수 있음. 사진은 늘 원본에서 편집해 상품 모습을 지킴 |
| 사실 검사를 기계 규칙 + 모델 판정 두 층으로 | 숫자는 규칙이 확실하고, 숫자가 아닌 사실은 모델이 필요함. 판정 실패 시 fail-closed |
| 도구 오류를 문장으로 반환 | 예외로 끝내지 않고 모델이 스스로 고치게. 4라운드 상한으로 무한 루프 방지 |
| LangGraph 체크포인트를 쓰지 않음 | 턴마다 `page.json` · `chat.json`을 이미 저장하므로 중복. 필요하면 SqliteSaver 추가 |
| 파인튜닝은 블라인드 승률 + 기계 지표 허용 폭으로 채택 | 손실 값이 아니라 사용자가 보는 결과로 판단. 지면 버림(판정 r1~r3, 문구 2-1) |

### 이력서용 문장

**짧게 (3줄)**
- 로컬 LLM(Qwen3.8-9B · Qwen-Image 2.1, MLX) 기반 대화형 상세페이지 에이전트를 1인 설계 · 구현했습니다(FastAPI · LangGraph · LangChain).
- 숫자 규칙 검사와 문장별 모델 판정의 두 층, fail-closed, 되묻기 도구로 환각을 막았습니다. 문구 LoRA SFT로 블라인드 승률 0.897을 얻었고, 근거 없는 문장 비율은 0.146에서 0.049로 줄었습니다.
- 교사와 무관한 블라인드 시험셋으로, 개발셋에서 좋아 보이던 판정 파인튜닝의 퇴행(잘못 거르기 0.057 → 0.46)을 찾아 채택을 막았습니다.

**길게 (항목형)**
- LangGraph 상태 그래프 2개를 설계했습니다(초안 7노드 고정 파이프라인, 채팅 model ⇄ tools 루프 · 도구 8개 · 4라운드 상한). 첫 초안은 60~87초, 문구 수정은 3.4초입니다.
- 직접 HTTP로 부르던 모델 층을 LangChain `ChatOpenAI`(bind_tools · json_schema 구조화 출력)로 옮겼습니다. 에이전트 · 서버 테스트는 고치지 않고 통과했고, 초안 시간은 +1.4%, 실모델 회귀는 12/13 · 8/8이었습니다.
- 평가 장치를 만들었습니다. 분류별 dev/test 분할, 좌우를 섞은 블라인드 A/B, 맥락 없는 판정자, 기계 지표 허용 폭, 학습 전 교사 관문이 들어 있습니다. 같은 장치로 프롬프트 개선안(test 0.414)은 버리고 SFT(test 0.897)는 채택했습니다.
- mlx-vlm LoRA(rank 16, 응답 부분만)로 학습하고 8bit로 병합해 서빙했습니다. 학습 데이터는 교사 초안 480개를 런타임 검사로 걸러 349행을 남긴 것입니다.
- LangSmith run 2만여 개를 API로 집계해 테스트에서 새던 추적을 찾았습니다. 원인을 찾아 고치고 회귀 테스트를 추가했습니다.
- 단위 테스트 181개(모델은 대본 가짜 객체)와 실모델 회귀(도구 13문항 · 판정 8문항)로 변경마다 검증했습니다.

### 면접에서 설명할 포인트

- **"파인튜닝이 성공했나요?"**
  - 판정은 실패를 일찍 알아내고 멈춘 사례입니다.
  - 문구는 관문 → 학습 → 블라인드 → 범위 제한까지 간 사례입니다.
  - 둘을 함께 말하면, 숫자를 고르는 기준이 있다는 것을 보여 줄 수 있습니다.
- **"환각은 어떻게 막나요?"**
  - 숫자는 규칙으로 막습니다(확실하고 빠름).
  - 숫자가 아닌 사실은 모델이 문장마다 판정합니다(fail-closed).
  - 꼭 필요한데 없는 사실은 되묻습니다.
  - 그래도 남는 한계가 있습니다. 판정기가 놓친 "습기나 물기에는 주의하세요"를 [알려진 제한](#limits)에 적어 두었습니다.
- **"왜 LangGraph인가요?"**
  - 초안은 순서가 고정된 파이프라인이고, 채팅은 조건부로 끝나는 루프입니다. 둘 다 상태 그래프로 쓰면 노드 단위로 테스트하고 추적할 수 있습니다.
  - 체크포인트는 일부러 쓰지 않았습니다. 저장은 이미 파일로 하고 있습니다.
- **"평가 판정자도 LLM인데 믿을 수 있나요?"**
  - 판정자는 맥락 없이 짝 파일만 보고, 어느 쪽이 새 모델인지 모릅니다.
  - 한계도 보고서에 적었습니다. 교사와 판정자가 같은 기준을 받는 구조라 교사를 닮을수록 유리할 수 있고, 상품 30개라 잡음이 큽니다.

### 남은 과제

- 문구 모델은 사진 한 장 초안에만 씁니다. 여러 장에도 쓰려면 사진 설명이 있는 학습 행으로 다시 학습해야 합니다.
- 2-2가 진 3건은 모두 한 페이지 안에서 같은 구절을 되풀이한 경우입니다. 다음 라운드의 목표입니다.
- 스크립트별 LangSmith 프로젝트 이름이 `.env`의 값에 덮이는 문제는 아직 고치지 않았습니다.

## 🏗️ 시스템 구성

<p align="center"><img src="docs/diagrams/system.png" alt="시스템 구성: 브라우저 → FastAPI 서버 → 에이전트 그래프 · 저장소 · 렌더 → 페이지 도구 · 모델 클라이언트 → MLX Serve" width="860"></p>

| 모듈 | 하는 일 |
|---|---|
| `pagegen.server` | FastAPI, 127.0.0.1:8000. 모델을 쓰는 요청은 한 번에 하나 |
| `pagegen.agent` | LangGraph 그래프 두 개: 첫 초안 · 채팅 한 턴 |
| `pagegen.page` | `page.json` 상태와 도구의 순수 로직 (숫자 · 최상급 · 한자 검사) |
| `pagegen.render` | `page.json` → HTML, Playwright로 PNG · JPG |
| `pagegen.store` | `projects/<id>/` 폴더 (사진 · `page.json` · `chat.json` · `versions/`) |
| `pagegen.llm` | MLX Serve 클라이언트. Qwen3.8-9B 4bit(분석 · 채팅 · 판정), 문구 SFT 8bit(사진 설명 없는 초안 문구), Qwen-Image 2.1(사진 편집) |

모듈 사이 호출 수는 [graphify](https://github.com/Graphify-Labs/graphify) 코드 그래프로 셌습니다. 대상은 `pagegen/` AST이고, 노드 211 · 엣지 443 · 커뮤니티 7입니다.

| 호출 | 수 | 내용 |
|---|---|---|
| agent → page | 24 | 도구 실행 · 문구 검사 · 섹션 조립 |
| server → store | 16 | 업로드 · 저장 · 되돌리기 · 파일 경로 |
| agent → llm | 11 | 분석 · 사진 설명 · 문구 · 판정 · 채팅 · 사진 편집 |
| server → agent | 2 | `make_draft` · `chat_turn` |
| server → render | 2 | 미리보기 HTML · 내보내기 |

- 연결이 가장 많은 노드는 `LLMError`와 `ToolError`(각 15)입니다. 특히 `LLMError`는 커뮤니티 5개를 잇습니다. 모델 오류가 서버 응답(502)까지 그대로 올라가는 구조이기 때문입니다.
- import 순환은 없습니다.
- 모델 호출은 LangChain `ChatOpenAI`가 MLX Serve로 보냅니다.
  - Qwen thinking은 `extra_body`로 넘깁니다.
  - 도구는 `bind_tools`, JSON은 `json_schema` 구조화 출력입니다.
  - 사진 편집은 OpenAI 표준 필드가 아니라서 직접 HTTP로 부릅니다.
- 서버는 초안 · 채팅 · 되돌리기 요청을 잠금 하나로 한 번에 하나씩 처리합니다.

## 🔄 처리 흐름

### 첫 초안 (고정 순서)

<p align="center"><img src="docs/diagrams/draft-graph.png" alt="첫 초안 LangGraph: 사진 분석 → 사진 설명 → 문구 작성 → 섹션 조립 → 사실 검사 → 연출 컷 → 첫 메시지, 분석 · 문구 · 검사 실패 시 초안 없음" width="860"></p>

```text
POST /projects  사진 + 상품명 + 설명
  → 업로드 저장 (원본 바이트 그대로, 형식 판별)
  → analyze       사진 최대 4장 + 설명 → 분류 · 보이는 특징 · 색 · 사실(facts) · 질문    (Qwen3.8-9B 비전)
  → caption       2 · 3번째 사진 설명                                              (Qwen3.8-9B 비전)
  → write_copy    hero · banner · points · scene · notice · details 문구            (COPY_MODEL 또는 TEXT_MODEL)
  → assemble      사진 배치대로 섹션 조립, 근거 있는 facts만 스펙 표로
  → check         모든 문구에 숫자 · 최상급 · 한자 검사, 문장마다 사실 판정            (원본 9B)
  → edit_scene    scene 섹션 사진을 연출 컷으로 편집 (실패하면 원본 유지)            (Qwen-Image 2.1)
  → first_message 초안 완료 + 빠진 정보 질문
```

- 분석과 문구를 두 번에 나눠 부릅니다. 한 번에 긴 JSON을 내게 하면 9B가 같은 문장을 반복하다 출력 한도에서 잘렸기 때문입니다.
- JSON이 깨지면 한 번 다시 부르고, 또 깨지면 오류를 보여주고 초안을 만들지 않습니다. 업로드 사진은 남습니다.
- 검사에 걸린 문장은 그 문장만 빼고, 비게 된 섹션은 정리합니다.

### 채팅 한 턴 (도구 호출)

<p align="center"><img src="docs/diagrams/chat-graph.png" alt="채팅 한 턴: 모델 호출 ⇄ 도구 실행, 텍스트 답장 · ask_user 질문 · 4라운드 도달로 끝남" width="860"></p>

| 도구 | 하는 일 |
|---|---|
| `update_text` | 섹션의 헤드라인 · 본문을 새 문구로 바꿈 |
| `edit_photo` | 섹션 사진의 업로드 원본을 편집해 연출 컷으로 교체 (약 1분) |
| `use_photo` | 이미 있는 사진(원본 · 이전 편집본)으로 교체. "원래 사진으로" |
| `add_section` | 지정한 섹션 다음에 새 섹션 추가 |
| `remove_section` | 섹션 삭제 |
| `move_section` | 섹션 순서 이동 |
| `set_variant` | 섹션 배치 · 모양 변경 (예: hero 글씨를 사진 위로) |
| `ask_user` | 꼭 필요한 제품 사실이 없을 때만 사용자에게 질문. 부르면 턴이 끝남 |

- 도구 오류(없는 id, 근거 없는 숫자 등)는 예외가 아니라 모델에게 돌려주는 문장입니다. 모델이 그 문장을 보고 다시 시도하거나 사용자에게 묻습니다.
- 모델 입력은 시스템 프롬프트(규칙 + 현재 `page.json`) + 최근 대화 6턴 + 이번 메시지입니다.

| 4번째부터 | `gallery` |

## 🖼️ 사진 처리 정책

- **업로드:** 최대 6장, 장당 20MB, 4천만 화소까지 받습니다.
  - Pillow로 형식을 판별해 JPEG · PNG · WebP만 받습니다. HEIC는 JPG로 바꿔 올려야 합니다.
  - 원본 바이트를 그대로 저장합니다.
- **편집:** Qwen-Image 2.1 `mode: edit`, `strength` 0.3입니다. 건당 약 46~47초 걸립니다.
  - 보내기 전에 EXIF 방향을 적용하고, 비율을 유지한 채 1024×1024 흰 캔버스 가운데에 넣습니다.
  - 프롬프트에 "제품의 모양, 색상, 로고와 무늬는 그대로 보존한다"를 붙입니다.
- **늘 원본에서 편집합니다.** 편집본을 다시 편집하지 않아 화질이 누적해 떨어지지 않습니다.
- **편집본은 연출용입니다.** 큰 형태 · 색 · 무늬는 유지하지만 작은 무늬 · 장식은 원본과 같지 않습니다. 정확한 디테일은 원본 사진이 보여줍니다.
- 편집에 실패하면 이전 사진을 그대로 두고, 채팅에 실패 사실을 남깁니다.

<a id="copy-safety"></a>

## ✍️ 문구 안전 정책

**근거 텍스트** = 상품명 + 설명 + 사용자가 채팅에 쓴 모든 메시지입니다. 사용자가 "350g이에요"라고 답하면 그 뒤로 350g은 근거가 있습니다.

```text
새 문구(헤드라인 · 본문)
  → 숫자 검사      근거 텍스트에 없는 (숫자, 단위)는 거절. "5"는 "500ml"로 근거가 생기지 않음
  → 최상급 · 한자  "최고 · 최초 · 1위 · 완벽 …"과 한자는 기계적으로 뺌
  → 스펙 표 검사   표의 값이 근거 텍스트에 그대로 있어야 함
  → 사실 판정      문장마다 원본 9B 판정 1회. 근거 없는 사실(기능 · 소재 · 성능 · 인증)이면 거절
                   감성 표현("하루를 산뜻하게")은 사실이 아니므로 통과
```

- **판정이 실패하면 반영하지 않습니다(fail-closed).** 한 번 다시 부르고, 또 실패하면 그 수정은 반영하지 않습니다.
- **판매자 주장은 근거입니다.** 사용자가 "식기세척기 사용 가능하다고 써줘"라고 하면 그대로 씁니다. 사실 여부의 책임은 판매자에게 있고, 에이전트가 막는 대상은 **모델이 스스로 덧붙인** 사실입니다.
- 사진에서 보이는 색 · 모양은 분석 결과가 근거입니다.
- 프롬프트만으로는 막히지 않았습니다. 스파이크에서 "지어내지 말라"고 명시했는데도 9B가 입력에 없는 "따뜻하고 차갑게"를 써 넣었습니다. 그래서 검사를 코드와 판정 모델로 겁니다.

| 상황 | 동작 |

## 💾 저장과 되돌리기

| 저장 대상 | 위치 (`projects/<id>/`) |
|---|---|
| 업로드 원본 · 편집본 | `photos/` (`p1.jpg`, 편집본은 새 파일) |

- 되돌리기는 도구가 아니라 화면의 버튼입니다. 가장 최근 `versions/` 파일을 `page.json`으로 복원하고 그 파일을 지웁니다. 사진 파일은 지우지 않습니다.

## ⚙️ 모델과 런타임

| 역할 | 모델 | 환경 변수 |
|---|---|---|
| 사진 분석 · 채팅 · 도구 선택 | `empero-ai/Qwen3.8-9B-Distill-MLX-4bit` | `TEXT_MODEL` |
| 첫 초안 문구 | `local/Qwen3.8-9B-pagegen-copy-r1-8bit` (2단계 SFT) | `COPY_MODEL` |
| 사실 판정 (문장마다) | 원본 9B | `JUDGE_MODEL` |

- `COPY_MODEL` · `JUDGE_MODEL`을 비우면 `TEXT_MODEL`을 씁니다.
- **문구 모델은 사진 설명이 없는 초안(사진 한 장)에만 씁니다.**
  - 사진이 여러 장이라 사진 설명이 붙으면 `TEXT_MODEL`이 씁니다.
  - 문구 모델은 사진 설명이 없는 입력으로만 학습 · 시험했습니다. 사진 설명 2개를 주면 `details` 개수를 10번 중 3번만 맞혔습니다(원본은 10/10).
- **MLX Serve 주의점**
  - 목록에 없는 모델 이름을 받아도 오류 없이, 이미 올라와 있는 모델로 답합니다. 이름을 정확히 적어야 합니다.
  - `~/.mlx-serve/models/`에 새 모델 폴더를 넣으면 MLX-Serve 앱을 다시 켜야 목록에 나옵니다.
  - LoRA 학습 중에는 요청을 거절할 수 있습니다.

## ▶️ 실행 방법

### 준비

1. MLX Serve 26.10.1 이상을 `http://127.0.0.1:11234`에서 띄우고, 위 모델을 서빙합니다.
2. 의존성과 PNG 렌더용 브라우저를 설치합니다.

```bash
uv sync
uv run playwright install chromium
```

### 서버

```bash
COPY_MODEL=local/Qwen3.8-9B-pagegen-copy-r1-8bit uv run python -m pagegen.server
```

`http://127.0.0.1:8000`을 열면 웹 화면이 나옵니다. `COPY_MODEL` 없이 띄우면 첫 초안 문구도 원본 9B가 씁니다.

### 스모크 실행

서버를 띄운 뒤, 사진 한 장으로 초안 · 수정 · 내보내기까지 돌리고 시간을 잽니다.

```bash
uv run python scripts/smoke.py --photo path/to/product.jpg --out path/to/out
```

## 🩺 운영과 관측

- **LangSmith는 개발 · 학습 데이터에만 씁니다.**

   - 데이터가 합성이라 정책 위반은 아니었습니다. 하지만 월간 한도를 썼습니다.
   - 고친 방법: `tests/conftest.py`가 추적 변수 네 개를 먼저 `false`로 고정합니다. `enable_dev_tracing`이 `setdefault`라서 이 값을 덮지 못합니다.
   - 회귀 테스트: `test_the_suite_sends_no_traces`. 고치기 전에는 이 테스트만 따로 돌리면 실패했습니다.
2. **스크립트가 정한 프로젝트 이름이 쓰이지 않습니다. (아직 고치지 않음)**
   - `judge_data.py`는 `pagegen-finetune`으로 보내도록 되어 있지만, 그 프로젝트는 없고 모두 `pagegen-dev`에 섞였습니다.
   - `enable_dev_tracing`이 `setdefault`라서, `.env`나 셸에 `LANGSMITH_PROJECT`가 있으면 그 값이 이기는 것으로 보입니다.

## ✅ 테스트와 평가

```bash
uv run pytest -q                       # 단위 테스트
uv run python scripts/eval_tools.py    # 실모델 회귀
```

**181개 테스트**가 실제 모델 호출 없이 통과합니다(2026-10-18). 테스트는 LangSmith로 추적을 보내지 않습니다. 모델은 대본대로 답하는 가짜 객체로 바꿔 끼웁니다. 검증 범위는 다음과 같습니다.

- 도구 로직: 섹션 추가 · 삭제 · 이동 · 변형, 숫자 · 최상급 · 한자 · 스펙 표 검사
- 첫 초안: 사진 배치, 사진 설명 실패 시 처리, 판정 fail-closed, 문구 모델 선택
- 채팅 루프: 도구 오류 반환, `ask_user` 종료, 4라운드 제한
- 저장: 업로드 형식 판별, 되돌리기, 파일 경로 검증
- 렌더 · 서버 · 화면: HTML, PNG 내보내기, API 오류 코드
- 파인튜닝 도구: 데이터 분할, 이어 쓰기 거부, 블라인드 짝 · 채점, 학습 행

```text
page-generation-v2/
├── pagegen/
│   ├── server.py      # FastAPI 앱 · API · 오류 처리 · 추적 끄기

│   ├── render.py      # page.json → HTML, Playwright PNG · JPG · 섹션 PNG

│   ├── smoke.py       # 초안 · 수정 · 내보내기 스모크와 시간 측정
│   └── finetune/      # 판정 · 문구 파인튜닝 데이터 · 평가 · 병합

└── pyproject.toml     # Python 3.13, uv
```

`projects/`(사용자 프로젝트)와 `.local/`(학습 데이터 · 어댑터), `.env`는 Git에 넣지 않습니다.

<a id="limits"></a>

## ⚠️ 알려진 제한

- **판정기가 일부 사실을 놓칩니다.** 실측에서 "습기나 물기에는 주의하세요"처럼 설명에 없는 관리 문구가 남은 적이 있습니다. 올리기 전에 문구를 직접 확인하세요.
- **한글 단위는 숫자만 비교합니다.** "3시간" · "2인분"처럼 한글 단위가 붙은 숫자는 단위를 보지 않고 숫자만 비교합니다. 단위가 틀린 경우는 사실 판정이 보완합니다.
- **문구 모델의 범위:** 2-2 모델은 사진 한 장 초안에만 씁니다. 그리고 한 페이지 안에서 같은 구절을 되풀이하는 약점이 있습니다. 시험에서 진 3건이 모두 이 경우였습니다. 사진 여러 장 초안에도 쓰려면 사진 설명이 있는 학습 행으로 다시 학습해야 합니다.
- **편집본의 디테일:** 작은 무늬 · 장식은 원본과 같지 않습니다.
- **처리 순서:** 모델을 쓰는 요청은 한 번에 하나씩 처리합니다. 사진 편집이 들어간 수정은 1분 가까이 걸립니다.
- **사진 형식:** HEIC는 받지 않습니다. JPG로 바꿔 올려야 합니다.
- **모델 이름:** `COPY_MODEL` · `JUDGE_MODEL`을 잘못 적으면, MLX Serve가 오류 없이 이미 올라온 모델로 답합니다. 앱은 이를 따로 확인하지 않습니다.
